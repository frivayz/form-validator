# Как мы работаем с задачами

Короткая памятка для команды: полный цикл от задачи до мержа.

## Порядок работы

1. **Задача (Issue).** Берём карточку из колонки `To Do` на Kanban-доске и
   переносим её в `In Progress`. Оформляем Issue по шаблону
   `.github/ISSUE_TEMPLATE/task.md`: заголовок, описание, критерии приёмки,
   метки (`bug`, `enhancement`, `documentation`), исполнитель.
2. **Ветка.** Создаём ветку от `main` с осмысленным именем:
   `feature/issue-<номер>-<краткое-описание>` или `fix/issue-<номер>-...`.
3. **Коммиты.** Делаем несколько атомарных коммитов, каждый со ссылкой на
   задачу в сообщении: `#12 Добавлена валидация email`.
4. **Pull Request.** Пушим ветку и открываем PR в `main`. В описании указываем
   `Closes #<номер>`, что сделано и как это проверить.
5. **Code Review.** Ревьюер изучает вкладку `Files changed`, оставляет 2–3
   содержательных комментария и выбирает `Approve` или `Request changes`.
6. **Правки.** Автор отвечает на замечания и пушит новые коммиты в ту же
   ветку — PR обновляется автоматически.
7. **Мерж.** После одобрения выполняем мерж, удаляем ветку, переносим карточку
   в `Done`. Issue закрывается автоматически по ключевому слову `Closes`.
8. **Синхронизация.** Переходим в `main`, выполняем `git pull` и убеждаемся,
   что изменения на месте.

## Соглашения по коммитам

| Префикс | Назначение |
|---------|------------|
| `feat:` | новая функциональность |
| `fix:` | исправление ошибки |
| `docs:` | документация |
| `test:` | тесты |
| `chore:` | служебные изменения |

## Локальная проверка перед PR

```bash
python -m unittest discover -s tests -v
```
